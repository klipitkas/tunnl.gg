# Request activity tracking — October 21, 2026

Request activity tracking now returns a small guard whose `End` method uses
the tunnel's existing mutex to protect both its completion flag and the
activity counters. This removes the completion closure and separate
`sync.Once` allocation from the ordinary deferred request path.

The baseline is the saved working tree after the callback-state, idle-channel
pool and request-logging improvements. It is not the HEAD commit alone.
No deadline, transport, logging, rate-limit or expiry policy changed here.

## Ownership and correctness

`BeginRequest` now returns `*RequestActivity`. Both production callers—the
HTTP handler, including WebSockets, and inspector replay—use:

```go
defer tun.BeginRequest().End()
```

The constructor calls a bookkeeping helper and returns the guard. Keeping
that constructor small lets Go inline it and keep the guard on the caller's
stack. The guard is not pooled. Sharing the returned pointer is safe;
copying the guard value is unsupported, as its API documentation states.
Code importing this package and using the previous returned function must
migrate to `.End()`.

Beginning activity still increments the in-flight count and refreshes
`LastActive` under the tunnel mutex. Completion checks and sets the guard's
flag under that same mutex, decrements the count once, and refreshes the
timestamp once. Repeated and concurrent calls wait for the locked update;
they cannot decrement twice or keep an otherwise idle tunnel alive.
Repeated completion now acquires the tunnel mutex rather than taking
`sync.Once`'s completed fast path. Ordinary requests complete once.

Tests cover 64 concurrent completions of one activity while another remains
active, duplicate completion without timestamp refresh, final idle expiry,
and deferred cleanup during panic. Existing tests cover inactivity during a
long-lived request and maximum lifetime even while a request remains active.
The focused lifecycle tests passed 20 repetitions under the race detector.

## Measurement method

Go 1.26.9, darwin/arm64, Apple M1 Pro, `GOMAXPROCS=8`, `CGO_ENABLED=0`,
`GOWORK=off`. Ten sequential samples per version, with before/after order
alternated within pairs. No profiling or validation jobs ran alongside the
timing comparisons; the machine is a shared desktop.

`BenchmarkRequestActivity` measures the same deferred begin/complete lifecycle
and timestamps in both versions. Only the completion syntax differs. The
handler benchmark is identical across versions and includes the real handler
with an in-process backend; it excludes TLS, SSH and session logging.

The unchanged opt-in relay harness uses real local TLS, HTTP/1.1 and HTTP/2,
SSH forwarding, a TCP backend and terminal logs delivered through the SSH
session. Each sample warms 16 requests, then schedules 180 at 100/s with four
workers. The mix is 90% empty GETs returning 1 KiB and 10% POSTs uploading
16 KiB and returning 64 KiB. It checks complete payloads, request identity,
status, protocol and log delivery. Every exit status is saved; failures are
not retried or replaced. This is a short burst-budget comparison, not a
capacity or sustainable-rate test.

## Results

| Case | Allocations before → after |
| --- | ---: |
| Activity begin + deferred completion | 2 → 0 |
| Handler GET, 1 KiB, IPv6 | 68 → 66 |
| Handler GET, 1 KiB, IPv4 | 66 → 64 |
| Handler GET, 64 KiB | 69 → 67 |
| Handler POST, 16 KiB upload | 76 → 74 |
| Inspected response, 16 KiB or 15,000 bytes | 76 → 74 |
| Missing tunnel, control | 26 → 26 |

Counts were identical across all ten samples per version. The isolated guard
also went from 40 to 0 allocated bytes per operation. Its median elapsed time
was 211.9 → 147.1 ns, but timing varied widely and the difference was not
statistically significant (`p=0.143`). All handler timing differences were
also inconclusive. The supported result is the allocation reduction.

All 40 protocol samples in the repeated forwarding comparison passed, with
zero dropped arrivals and every payload and request log verified: 3,600
measured requests and 3,920 logs including warmup per revision.

| Full-process metric, median across samples | HTTP/1.1 before → after | HTTP/2 before → after |
| --- | ---: | ---: |
| Allocations/request | 239.9 → 238.1 | 270.8 → 268.7 |
| Allocation reduction | 0.79% | 0.80% |
| p50 latency | 1.492 → 1.502 ms | 1.605 → 1.561 ms |
| p95 latency | 1.977 → 2.032 ms | 2.374 → 2.103 ms |
| p99 latency | 3.249 → 3.643 ms | 4.281 → 2.942 ms |

Process allocation counts include the clients, backend and logging, not just
the relay. Both allocation reductions were significant (`p<0.001`). Byte
reductions were inconclusive. HTTP/2 p95 improved in this run (`p=0.029`),
but this isolated result among several comparisons, on a shared machine,
does not establish a general latency improvement. Other latency differences
were inconclusive. No CPU, retained-heap, RSS or maximum-capacity claim is made.

Separate allocation profiles verify the mechanism. Over 392 forwarded requests
per version, including warmups and both protocols, `BeginRequest` previously
allocated 784 objects. The candidate activity path allocated none. Both
instrumented forwarding runs also passed; their timings are excluded from the
comparison. A separate isolated profile showed 40,002 guard objects before
and none after over 20,001 calls including benchmark calibration.

Compiler escape analysis confirms `RequestActivity` stays off the heap at
both the actual HTTP handler and inspector replay call sites. This result is
for the measured Go version and normal deferred use; retaining a guard or
sharing it with another goroutine may require a heap allocation.
