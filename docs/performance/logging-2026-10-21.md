# Request logging and success-path allocations — October 21, 2026

Request logs now write terminal columns directly into the existing pooled
buffer. JSON logs keep their optional numbers inside the encoding record.
The HTTP handler also avoids allocating an upload counter for recognized
empty bodies, skips error inspection on successful requests, and uses the
canonical Cloudflare header spelling when deleting an untrusted header.

These are incremental changes after the proxy callback-state consolidation
and idle-channel pool increase to 32. The baseline is a saved working-tree
snapshot, **not HEAD** (`8cd8933e22f5d1db2431d3bda9ae988e0f600366`). Both
versions use the same benchmarks and JSON-capable TLS/SSH harness.

## Compatibility and mechanism

The terminal formatter uses `time.Time.AppendFormat` and `strconv.AppendInt` /
`AppendFloat` with stack scratch storage, then writes into the logger's
existing buffer. Padding still counts Unicode runes and uses minimum column
widths. Target shortening and terminal escaping retain their existing code.
The JSON encoder, field order, tags, HTML escaping policy and CRLF terminators
are unchanged. Optional numeric pointers refer to fields in one record;
explicit zero bytes and sub-millisecond durations remain distinguishable from
absent values.

`TestRequestLogFormattingCompatibility` compares the old and new formatters
byte-for-byte over 1,000 cases, including Unicode, invalid UTF-8, control
characters, long methods and paths, status classes, tunnl-generated events,
notes, details and numeric boundaries. Existing tests cover concurrent log
ownership, batching, closure, traffic counters, proxy errors, spoofed forwarding
headers, unknown-length upload limits and slow uploads.

The handler only skips its upload counter when the body is nil or
`http.NoBody`; it does not infer emptiness from `ContentLength`. Other bodies,
including unknown-length uploads, still get counted. Error descriptions and
header-deletion semantics stay the same.

## Isolated measurements

Go 1.26.9, darwin/arm64, Apple M1 Pro, `GOMAXPROCS=8`, `CGO_ENABLED=0`,
`GOWORK=off`. Ten sequential samples per revision, alternating execution
order within each pair. Logger samples use a 300 ms benchmark duration;
handler samples use 20,000 iterations per case. Profiling and validation jobs
run separately from timing comparisons. The machine is a shared desktop.

The logger benchmark acknowledges every write: dropped logs cannot make it
look faster. It includes formatting, queueing and the drain goroutine, with
an acknowledged in-memory sink rather than SSH. Results apply to the ordinary
short request entry in this benchmark; escaping, long paths and buffer growth
can still allocate.

| Logger | Allocations/entry before → after | Bytes/entry before → after | Median time before → after |
| --- | ---: | ---: | ---: |
| Terminal | 14 → 0 | 224 → 0 | 1.621 → 0.824 µs |
| JSON | 4 → 2 | 320 → 184 | 0.984 → 0.923 µs |

The isolated handler benchmark excludes session logging, TLS and SSH, so it
measures the three smaller handler changes independently of log formatting.

| Handler case | Allocations/request before → after |
| --- | ---: |
| GET, 1 KiB, IPv6 | 71 → 68 |
| GET, 1 KiB, IPv4 | 69 → 66 |

## Full forwarding measurements

The opt-in `TestRelayPerformance` exercises certificate-verified local TLS,
HTTP/1.1 and HTTP/2, real SSH forwarding, a TCP backend and logs delivered
through the SSH session. Terminal and JSON sessions are measured separately.
Each sample warms 16 requests, then schedules 180 requests at 100/s, with four
workers and a bounded queue. The mix is 90% empty GETs returning 1 KiB and 10%
POSTs uploading 16 KiB and returning 64 KiB. It checks protocol, status,
request identity, complete payloads and delivery of every log. Latency includes
generator scheduling and queue delay.

An initial series stopped during the fourth pair: the candidate HTTP/2 sample
dropped one scheduled arrival when the generator queue filled. Tail latency
was noisy on both revisions. The entire interrupted series is retained
separately; a fresh, complete series records every exit status without retries.
This observation must not be hidden behind successful samples or interpreted
as a demonstrated application regression or improvement.

The complete series attempted ten samples per revision, protocol and log mode
(80 protocol subcases). Three subcases failed the arrival-drop check:

- Terminal baseline, HTTP/1.1, sample 8: one dropped arrival.
- Terminal candidate, HTTP/2, sample 3: six dropped arrivals.
- JSON baseline, HTTP/2, sample 1: one dropped arrival.

The other 77 subcases passed their payload and log-delivery checks. There
were no retries. The table below describes **successful subcases only**; the
missing samples and desktop scheduling variability limit interpretation.

| Mode / protocol | Successful samples before / after | Process allocations/request before → after | p95 before → after | p99 before → after |
| --- | ---: | ---: | ---: | ---: |
| Terminal / HTTP/1.1 | 9 / 10 | 256.3 → 243.4 | 2.082 → 2.789 ms | 4.573 → 9.635 ms |
| Terminal / HTTP/2 | 10 / 9 | 286.1 → 271.1 | 2.213 → 2.345 ms | 3.688 → 5.060 ms |
| JSON / HTTP/1.1 | 10 / 10 | 248.2 → 244.4 | 2.056 → 2.338 ms | 3.931 → 6.476 ms |
| JSON / HTTP/2 | 9 / 10 | 278.1 → 273.9 | 2.549 → 2.854 ms | 5.712 → 6.231 ms |

These are medians across samples. All clients, the backend, the relay and
session logging share the process, so allocations are not relay-only costs.
HTTP/2 allocation reductions are consistent with the isolated mechanism;
HTTP/1.1 allocation differences were statistically inconclusive. Allocated
bytes were also inconclusive. Candidate tail medians were higher in all four
cases, with wide intervals and no statistically significant latency differences.
That does **not** establish equivalent tails or rule out a regression.

This change demonstrates fewer allocations and faster isolated logging. It
does not demonstrate improved forwarding latency, CPU usage, RSS or capacity.
A dedicated, quiet load-test environment is needed for useful tail comparisons.
The offered rate fits short-run burst budgets and is not a sustainable-rate
or maximum-capacity claim.

## Profiles and validation

Separate full-allocation profiles support the mechanism: the candidate logger
profile attributes the steady-state allocations to the JSON record and its
formatted timestamp; terminal formatting no longer contributes heap objects.
The handler GET profile loses 2,001 direct handler allocations and 2,001
`describeProxyError` allocations over 2,001 invocations (including benchmark
calibration), alongside the removed header canonicalization allocation.
Tiny allocation packing means profile object counts need not match benchmark
`allocs/op` for every individual formatter call.

Validation passed:

- Focused server/tunnel tests and byte-for-byte formatter compatibility.
- `GOWORK=off GOTOOLCHAIN=go1.26.9 go test -race ./...`.
- `go vet ./...`, `CGO_ENABLED=0 go build ./...` with the same toolchain.
- golangci-lint 2.14.0: zero issues.

The opt-in forwarding comparison had the queue-limit failures recorded above;
it is not reported as an entirely passing suite. No production changes were
applied or deployed.

do not mix instrumented timings into the comparisons.
