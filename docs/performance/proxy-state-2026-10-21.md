# Proxy callback allocations — October 21, 2026

The HTTP proxy now keeps its mutable callback state in one request-local
struct. This removes five heap allocations from every proxied request. It
does not establish a meaningful latency, CPU or capacity improvement.

Baseline: `8cd8933e22f5d1db2431d3bda9ae988e0f600366`. No production service,
configuration, dependency or rate limit was changed.

## Evidence and hypothesis

The earlier allocation report and the cloud repository's October 20 workload
report were starting context, not measurements of this change. The latter
describes mostly bodyless requests and small responses, with substantial
network/client delays. Its production raw telemetry was not available in
these local checkouts, so those distributions were not independently verified.
An archived October 16 load-test CPU profile was available and was inspected;
fresh profiles and comparisons below determine the result.

A new full-allocation profile of the current handler and compiler escape
analysis agreed: `respBody`, `outHost`, `outHeader`, `respHeader`, `proxyErr`
and `body` each escaped separately through the reverse proxy callbacks.
Four are inspector state, allocated even when inspection is disabled. This
was the largest directly attributed group of avoidable allocations inside
the handler itself, not the application's dominant CPU or latency cost.

Hypothesis, stated before editing: grouping those six variables into one
request-local struct should remove exactly five allocations per proxied
request, including uploads and inspected responses. Failure to observe that
reduction would disprove the proposed mechanism. Error handling, capture
ownership, response limits, metrics and deferred logging retain the same
operations and order; the struct is neither shared across requests nor pooled.

Fresh profiles through real TLS/SSH forwarding confirm the mechanism. Across
392 requests (two protocols, each with 16 warmups and 180 measured requests),
the six original variables allocated 2,352 objects. The replacement struct
allocated 392: exactly 1,960 fewer objects, or five per request.

Separate CPU profiles of three full-path runs per version were dominated by
syscalls and runtime scheduling. They sampled 830 ms before and 970 ms after
over approximately 11 seconds each, including fixtures and setup. These short
diagnostic runs do not demonstrate a CPU saving. Allocation profiling was
performed separately, and instrumented runs were excluded from timing
comparisons, following the [Go diagnostics guidance](https://go.dev/doc/diagnostics).

## Controlled handler measurements

Go 1.26.9, darwin/arm64, Apple M1 Pro, `GOMAXPROCS=8`, `CGO_ENABLED=0`,
`GOWORK=off`. Both test binaries use the same harness and normal compiler
optimizations. Ten samples per version, 20,000 iterations per case per sample.
Each pair alternates before/after and after/before; runs are sequential.
No other validation or profiling jobs ran alongside these comparisons.

The benchmark's recorder now accepts read/write deadlines, as a real HTTP
writer does. This avoids counting unsupported-operation errors generated by
`httptest.ResponseRecorder`. **Both revisions use this corrected harness.**
Absolute counts should not be compared with the earlier report's harness.
Request construction and response buffering are still included; TLS, SSH,
socket traffic and session logging are excluded from this isolated benchmark.

| Case | Allocations before → after | Allocations change | Median time before → after |
| --- | ---: | ---: | ---: |
| GET, 1 KiB, IPv6 | 76 → 71 | −6.58% | 7.473 → 7.259 µs |
| GET, 1 KiB, IPv4 | 74 → 69 | −6.76% | 6.991 → 6.880 µs |
| GET, 64 KiB | 77 → 72 | −6.49% | 22.978 → 22.395 µs |
| POST, 16 KiB upload | 83 → 78 | −6.02% | 8.187 → 8.257 µs |
| Inspected, 16 KiB response | 84 → 79 | −5.95% | 15.077 → 14.585 µs |
| Inspected, 15,000-byte response | 84 → 79 | −5.95% | 15.105 → 14.732 µs |
| Missing tunnel, control | 26 → 26 | unchanged | 2.597 → 2.586 µs |

Allocation counts were identical within each version across all ten samples.
Benchstat found no significant timing difference in six of seven cases.
The inspected 16 KiB case improved 3.27% (`p=0.035`); this single result among
multiple comparisons is not evidence of a general latency improvement.
Allocated-byte reductions were small: the ordinary IPv6 GET went from a
median 11,173 to 11,164 B/op. Reducing object count does not imply a similar
percentage reduction in bytes or retained heap.

## Full forwarding comparison

`TestRelayPerformance` is opt-in and exercises real certificate-verified TLS,
HTTP/1.1 and HTTP/2, SSH forwarding, a TCP backend, and request logging through
the SSH session. Each sample warms 16 requests, then schedules 180 arrivals
at 100/s with four workers and a bounded queue. It checks status, protocol,
request identity, complete response contents, uploaded contents and delivery
of every request log. Failures or dropped arrivals fail the run. Latency starts
at the intended arrival time, including scheduling and queue delay.

The synthetic mix is 90% bodyless GETs returning 1 KiB and 10% POSTs uploading
16 KiB and returning 64 KiB. It approximates common operation shapes, not the
complete production distribution. Each short run fits the existing token
bucket burst budget; 100/s on one tunnel is not a sustainable rate claim.

Ten interleaved samples per version and protocol produced 3,600 measured
requests per version. All completed correctly, with zero dropped arrivals
and all 3,920 logs per version delivered, including warmups.

| Metric, median across samples | HTTP/1.1 before → after | HTTP/2 before → after |
| --- | ---: | ---: |
| Process-wide allocations/request | 261.06 → 256.28 | 291.03 → 286.79 |
| Allocations change | −1.83%, p=0.001 | −1.45%, p<0.001 |
| Process-wide allocated bytes/request | 64,430 → 65,245 | 74,850 → 76,104 |
| p50 latency | 1.554 → 1.550 ms | 1.635 → 1.648 ms |
| p95 latency | 2.111 → 2.071 ms | 2.325 → 2.309 ms |
| p99 latency | 3.495 → 3.600 ms | 4.182 → 4.667 ms |

All clients, backend, logging and relay share the measurement process, so
these allocation totals are not isolated relay costs. Byte differences and
all latency differences were statistically inconclusive. Tail intervals were
wide; this is not a tight guarantee against tail-latency regressions.
Completed throughput followed the fixed arrival rate, about 100/s, and does
not measure maximum capacity. No lower RSS or retained-heap claim is made.

To reproduce in fresh directories, extract the baseline commit with
`git archive`, copy the current `pkg/server/allocations_bench_test.go` and
`pkg/server/relay_performance_test.go` into it, then build each revision's test
binary with the same Go version and environment:

```sh
GOWORK=off GOTOOLCHAIN=go1.26.9 CGO_ENABLED=0 \
  go test -c -o /absolute/path/to/before.test ./pkg/server
# Run from the candidate checkout, using after.test as the output path.
```

For each binary, collect ten samples with alternating version order. Use
separate output files for the handler and relay measurements:

```sh
GOMAXPROCS=8 /absolute/path/to/before.test -test.run '^$' \
  -test.bench '^BenchmarkRequestAllocations$' -test.benchtime=20000x -test.count=1
TUNNL_PERF=1 GOMAXPROCS=8 /absolute/path/to/before.test \
  -test.run '^TestRelayPerformance$' -test.v
```

Compare the raw outputs with
[`benchstat`](https://pkg.go.dev/golang.org/x/perf/cmd/benchstat), version
`golang.org/x/perf@v0.0.0-20261009192801-be2c69fb417e` for this report. That
analysis tool was built with Go 1.26.10; both measured application binaries
were built with Go 1.26.9. For diagnostic runs, separately add either
`-test.cpuprofile=cpu.out` or
`-test.memprofile=allocs.out -test.memprofilerate=1`, then use
`go tool pprof -sample_index=alloc_objects -list 'Server.*ServeHTTP' BINARY allocs.out`.

## Validation

Passed with Go 1.26.9 and `GOWORK=off`:

- `go test -race ./...`.
- `TUNNL_PERF=1 go test -race ./pkg/server -run '^TestRelayPerformance$' -count=1`.
- `go vet ./...` and `CGO_ENABLED=0 go build ./...`.
- golangci-lint 2.14.0, matching CI: zero issues.

Existing end-to-end tests cover inspector capture and replay, upload limits,
streaming, cancellation, proxy failures, cut-off response logging, traffic
accounting and WebSockets. The measured result supports retaining this small
allocation reduction; it does not support a claim that production requests
are faster or the service can handle more traffic.
